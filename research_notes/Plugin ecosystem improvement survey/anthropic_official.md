## 2. anthropics/skills and anthropics/claude-plugins-official

### Takeaway
`anthropics/skills` is the reference skill library (document skills plus examples, spec, template); `claude-plugins-official` is the curated marketplace with internal `/plugins` and partner `/external_plugins`. The best-engineered design to copy is the document skills: task routing, bundled validators, and mandatory render-and-inspect QA; and skill-creator for evals.

### Cited Findings
- `anthropics/skills`: folders `skills/`, `spec/`, `template/`; categories Creative and Design, Development and Technical, Enterprise and Communication, Document Skills (docx, pdf, pptx, xlsx). Only `name` and `description` required. Install via `/plugin marketplace add anthropics/skills`, then `document-skills@anthropic-agent-skills` or `example-skills@anthropic-agent-skills`. Document skills are "source-available, not open source"; others mostly Apache 2.0; repo says skills are "for demonstration and educational purposes" and to test before relying on them. Read. — [anthropics/skills](https://github.com/anthropics/skills)
- pptx skill: frontmatter with trigger description and license; task-routing table (create with pptxgenjs, edit by unzip/XML/rezip, read with markitdown); scripts `thumbnail.py`, `add_slide.py`, `clean.py`, `validate.py` (with `--original`), `soffice.py`; required 3-part QA (content dump, schema validate, render to PDF then JPEG and inspect every slide); about 2,500 words. Read (raw SKILL.md). — [pptx/SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/pptx/SKILL.md)
- skill-creator folder: `agents/` (grader.md, comparator.md, analyzer.md), `assets/` (eval_review.html), `eval-viewer/` (generate_review.py), `references/` (schemas.md), `scripts/` (aggregate_benchmark, run_loop, run_eval, package_skill). Workflow: draft; 2-3 test prompts in `evals/evals.json`; with-skill and baseline run per case (baseline = no skill, or snapshot of old skill); grader writes `grading.json` (text, passed, evidence); aggregate to `benchmark.json`; human review in viewer; iterate. Description optimization: about 20 realistic trigger queries including near-miss negatives, split 60/40 train/test, pick the best description by test score. Advice: make description "somewhat pushy" to avoid undertriggering; explain the why instead of rigid MUSTs; bundle scripts that subagents independently rewrote. Read (raw SKILL.md). — [skill-creator SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md)
- `claude-plugins-official`: `/plugins` (Anthropic-maintained) and `/external_plugins` (partners, community, approved after quality and security review via a submission form); install `/plugin install {name}@claude-plugins-official`; warning that Anthropic "does not control what MCP servers, files, or other software are included in plugins" and cannot verify they won't change; the marketplace `name` is a permanent slug (use `displayName` to relabel, `renames` map if unavoidable); skill-only repos can be listed with `strict: false` plus a `skills` array and a pinned `sha`. Read. — [claude-plugins-official](https://github.com/anthropics/claude-plugins-official)
- Reserved names: `claude plugin validate` errors on plugin names starting `claude-`, `anthropic-`, `anthropics-`, `cc-plugin-`, or `claude`/`anthropic` alone; exact official marketplace names (e.g. `claude-plugins-official`) cannot be used by third parties. Read. — [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)

### Inferences
- Our `slides` and `plotting` skills could adopt the pptx pattern: a routing table, bundled validators (we have `check_svg.py`), and a mandatory render-then-view step (our plotting already mandates a legibility check, so this largely matches).
- We have no eval suite; skill-creator's trigger-query set with near-miss negatives and train/test split is directly reusable for tuning our 24 descriptions, which probably overlap (e.g. `writing` vs `translator` vs `project-readme`).
- Third-party plugin names in our name space are fine (`bioinfo-lab`); no reserved-word conflict.

## 3. Agent Skills specification and authoring best practices

### Takeaway
Hard limits: name 64 chars lowercase/digits/hyphens, description 1,024 chars, SKILL.md under 500 lines (spec suggests under 5,000 tokens), references one level deep. Anthropic's central advice: be concise, write descriptions in third person with "what and when", build evals first, test on Haiku, Sonnet, and Opus.

### Cited Findings
- Spec fields: `name` (1-64, no leading/trailing/consecutive hyphens, must match directory), `description` (1-1024), optional `license`, `compatibility` (max 500), `metadata` (string map), `allowed-tools` (space-separated, "Experimental", support varies). Progressive disclosure: metadata about 100 tokens, body under 5,000 tokens recommended, resources on demand; under 500 lines; one-level-deep references; validate with `skills-ref validate ./my-skill`. Read. — [agentskills.io/specification](https://agentskills.io/specification)
- Best practices (Anthropic docs): context window is "a public good"; assume Claude is smart, challenge each paragraph's token cost; match freedom to fragility (high/medium/low); description in third person, specific, with triggers (avoid "Helps with documents"); names preferably gerund (`processing-pdfs`); avoid reserved words `anthropic`, `claude` in names; keep SKILL.md under 500 lines; reference files over 100 lines get a table of contents; avoid nested references (Claude may `head -100` partial reads); avoid time-sensitive text (use an "old patterns" section); consistent terminology; give a default tool rather than many options; scripts should "solve, don't defer" with explicit error handling and no "voodoo constants"; state whether to run or read a script; plan-validate-execute for batch or destructive work with verbose validator errors; fully qualified MCP names `Server:tool`; list package dependencies; forward slashes. Read. — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Testing advice: create evaluations before extensive docs; at least three evals; baseline without the skill; test with Haiku, Sonnet, Opus; "Claude A writes, Claude B tests" iteration. The page says there is "not currently a built-in way" to run these evals (this page is older than `claude plugin eval`; see section 4). Read. — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Engineering post (2025-10-16, possibly outdated): three-level progressive disclosure; security guidance: install only from trusted sources, audit bundled files (scripts, dependencies, images), watch for instructions that connect to untrusted external sources, malicious skills can exfiltrate data. Read. — [Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Claude Code skills docs add: frontmatter `when_to_use`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork` with `agent`, `paths` (glob-limited auto activation), `hooks`, `shell`, `arguments`/`argument-hint`; listing text (`description` + `when_to_use`) truncated at 1,536 characters, so put the key use case first; after auto-compaction the latest invocation of each skill is re-attached (first 5,000 tokens each, 25,000 combined); `` !`cmd` `` dynamic context injection; `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`; live reload of SKILL.md edits; on claude.ai uploads and the Skills API only `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` are accepted (other fields hard-error). Read (first 100k of 118k chars). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- `/skill-doctor` (v2.1.252+): reports per-skill context cost and usage, flags never-invoked skills. Read. — [Claude Code skills](https://code.claude.com/docs/en/skills). Note: unrelated community plugins also named "skill-doctor" exist; do not confuse. — [search](https://amaljithkuttamath.github.io/work/skill-doctor)
- "Lessons from Building Claude Code: How We Use Skills" (Thariq, reported 2026-03-17): hundreds of internal skills, nine categories, skills start small and grow with gotchas, verification skills most valuable. Search only (original not opened; only secondary write-ups). — [summary](https://vionwinnie.github.io/engineering/lessons-from-building-claude-code-skills)

### Inferences
- Our description fields should be audited against: third person, 1,024-char cap, key trigger within the first 1,536 chars of description + when_to_use. Ours begin "Use when ..." (second-person-ish imperative), which differs from Anthropic's third-person recommendation; Anthropic's own bio-research and skills repos also use "Use this skill when..." so both styles evidently trigger; low priority unless evals show misfires.
- A lab-rules skill preloaded by all agents is a context cost on every agent run; `/skill-doctor` and the 500-line guideline are the check.
- `paths:` and `disable-model-invocation` could cut description-listing load for niche skills (e.g. `variant-interpretation`, `genomic-prediction`).
- Gerund naming is a preference, not a rule; renaming 24 skills is not worth it.

### Gaps
- Spec has no versioning mechanism beyond free-form `metadata.version`.
- Primary text of the "How We Use Skills" post not read.
- The "skill not triggering" troubleshooting section of the Claude Code skills page was truncated and not read.

## 4. Current Claude Code plugin features we may not use

### Takeaway
Plugins can bundle hooks, MCP, LSP, monitors, output styles, workflows, themes, `bin/` executables, `userConfig`, default `settings.json` (only `agent`, `subagentStatusLine`), and dependencies. There is a native `claude plugin validate` and `claude plugin eval` (v2.1.269+) with a no-plugin baseline. Plugin subagents have restricted frontmatter.

### Cited Findings
- `plugin.json`: only `name` required (kebab-case; every component namespaced `plugin:component`). Fields include `displayName`, `version` ("setting it keeps users on that version until you change it"; not checked against semver), `dependencies`, `defaultEnabled`, `userConfig` (typed prompts, `sensitive` stored in secure storage, `${user_config.KEY}`), `hooks`, `mcpServers` (also `.mcpb` bundles), `lspServers`, `outputStyles`, `workflows`, `commands` object map, `settings`, `experimental.{themes,monitors,evals}`. Unknown top-level fields are stripped with a warning. Read. — [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- `${CLAUDE_PLUGIN_ROOT}` changes on update; `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`) persists across updates; these variables are not in the Bash tool environment, only in hooks, MCP, LSP, and markdown bodies. A `CLAUDE.md` at the plugin root is not loaded (validate warns); put instructions in a skill. `bin/` executables are put on the Bash PATH. Read. — [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- `claude plugin validate ./plugin` (and for marketplaces); `--strict` makes warnings fail in CI. Read. — [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)
- `claude plugin eval`: requires v2.1.269+; `evals/<case>/prompt.md` plus `graders/*.md` (regex, tool-used, `llm` rubric graders); 3 runs per case by default, with-plugin vs no-plugin baseline, columns WITH, W/OUT, delta; `claude plugin eval init` drafts cases interactively, including prompts that should NOT trigger; `--threshold` gates CI; every run is a real model call billed to the account; a typical first finding is `tool_used: Skill` failing, meaning the description does not trigger on natural phrasing. skill-creator is a separate per-skill alternative with a different format. Read (first part of a 62 KB page). — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals.md)
- Marketplace: `.claude-plugin/marketplace.json` needs `name`, `owner`, `plugins`; sources: relative path, `github`, `git-subdir`, `url`, `archive`, `npm`, `command`, pin with `ref`/`sha`; entry name must equal manifest name; local-path marketplaces pick up edits on `/reload-plugins` without a version bump, while hosted copies are cached. Read. — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Versions and update flow details are on pages not fetched (`plugins/loading.md#versions-and-updates`, `plugins/host-marketplace.md#keep-users-up-to-date`). Not read.
- Hooks: events include SessionStart (matchers startup, resume, clear, compact, fork), PreToolUse, PostToolUse, SubagentStart/Stop, PreCompact/PostCompact, InstructionsLoaded, FileChanged, and more; handler types command, http, mcp_tool, prompt, agent (experimental); PreToolUse can `deny` or rewrite `updatedInput`; `onFailure: "block"` makes a hook fail closed (v2.1.295+); docs call hooks "best-effort guardrails" and recommend permissions for hard rules; re-inject context after compaction with SessionStart matcher `compact`; write `additionalContext` as factual statements (imperative system-style text can trip injection defenses). Read (first 100k of 286k chars). — [Hooks](https://code.claude.com/docs/en/hooks)
- Monitors (`experimental.monitors`): persistent background commands, start `always` or `on-skill-invoke:<skill>`; do not start with `-p`; no `${user_config.*}` access. Read. — [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Subagent frontmatter: `name`, `description`, `tools`, `disallowedTools`, `model` (sonnet/opus/haiku/fable/ID/inherit), `permissionMode`, `maxTurns`, `effort` (low..max), `skills` (full content preloaded, up to 32), `mcpServers`, `hooks`, `memory` (user/project/local; project is the recommended default; first 200 lines or 25 KB of MEMORY.md injected), `background`, `isolation: worktree`, `omitClaudeMd` (v2.1.271+), `autoCompactWindow` (v2.1.296+), `initialPrompt`, `color`. IMPORTANT: for plugin-shipped subagents `hooks`, `mcpServers`, and `permissionMode` are ignored; ship hooks and MCP at plugin level. Combined custom subagent descriptions over 15,000 tokens trigger a startup warning; put detail in the body. "Use proactively" in a description encourages auto-delegation. Read (first 100k of 116k chars). — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Full list of `/plugin` install flow: `claude plugin marketplace add owner/repo`, `claude plugin install name@marketplace`. Read. — [knowledge-work-plugins](https://github.com/anthropics/knowledge-work-plugins)
- Tool launch date for `plugin eval` (2026-09-11, v2.1.269) comes from a third-party article; the docs confirm only the version requirement. Search only. — [claude-codex.fr](https://claude-codex.fr/fr/content/tester-ses-plugins-avec-plugin-eval/)

### Inferences
- Candidates for adoption, in rough order of value: (1) `claude plugin validate --strict` and `claude plugin eval` in CI with 3 to 5 trigger and non-trigger cases per key skill (writing, plotting, translator, lab-team); (2) a `hooks/hooks.json` that mechanically enforces rules now only stated in prose (e.g. PreToolUse deny of writes outside the working directory or of `/raid/tmp` listing, SessionStart `compact` matcher to re-inject the lab-rules essentials after compaction), noting that hooks are best-effort and need `onFailure: block` for fail-closed; (3) `userConfig` for per-user values (e.g. author name, default machine) instead of hard-coding; (4) `memory: project` on selected agents (reviewer, data-steward) if cross-session learning is wanted; (5) `.mcp.json` shipping PubMed/bioRxiv; (6) `effort` and `model` frontmatter, which we already use per the lab-team roster.
- Because plugin agents cannot use `permissionMode`, `hooks`, or `mcpServers`, safety for our agents must live in plugin-level hooks or the user's settings, not in agent files.
- `settings.json` in a plugin can set only `agent` (make a lab persona the main thread) and `subagentStatusLine`.
- The existing `update` skill should align with the real update mechanics: pinned `version` means users get updates only when we bump it.

## 5. Multi-agent research systems and context engineering

### Takeaway
Anthropic measured agents at about 4x chat tokens and multi-agent at about 15x, and says multi-agent only pays for high-value, parallelizable, breadth-first work; coding-like tasks with shared context are a poor fit. Subagents are for context isolation and return condensed summaries.

### Cited Findings
- Multi-agent research system (2025-06-13, over 12 months old, possibly outdated on model names but the lessons are cited widely): agents about 4x and multi-agent about 15x chat tokens; token usage explained about 80% of BrowseComp variance; Opus 4 lead with Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on the internal research eval; good fit = valuable, heavily parallel work exceeding one context window; poor fit = shared context or many dependencies "such as most coding work"; each subagent needs an objective, output format, tool/source guidance, and boundaries (vague briefs caused duplicated work); effort-scaling rules (simple fact: 1 agent, 3-10 calls; comparisons: 2-4 subagents, 10-15 calls each; complex: 10+); eval: start with about 20 real queries, LLM judge with rubric (accuracy, citation accuracy, completeness, source quality, tool efficiency), single prompt scoring 0-1 most consistent, plus human testing; for stateful agents judge the end state. Read. — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Context engineering (2025-09-29, over 12 months old): keep lightweight references and load just in time; compaction; note-taking to files (NOTES.md or to-do); sub-agents with clean contexts returning about 1,000 to 2,000 token summaries; principle "smallest set of high-signal tokens". Read. — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code subagent docs: delegate when a side task floods context with output you will not reuse, when tool restrictions are needed, for self-contained summarizable work, or to route cheap work to a lower-cost model; stay in the main thread for iterative back-and-forth, shared multi-phase context, quick targeted edits, or latency-sensitive work (a non-fork subagent starts fresh). Read. — [Subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
- This matches our "PI does thinking and small tasks itself; delegate only for isolation, independence, parallelism, long jobs" rule; it is supported by Anthropic's own guidance. Add the 15x cost figure as the rationale and an explicit "brief template" (objective, output format, tools/sources, boundaries) to `lab-team`, since Anthropic found vague briefs cause duplicate work.
- A lightweight eval (about 20 representative lab tasks, rubric judge) is the Anthropic-recommended way to test whether delegation rules help; cost-benefit is unproven for a small lab.
- The reviewer agent fits "independent read" use; the docs' point that subagent results should be condensed supports requiring compact returns (already in our assistant description).

### Gaps
- No Anthropic figure found on cost or quality of multi-agent for bioinformatics specifically.
- Newer (2026) Anthropic posts on agent teams or workflows were not searched in depth; the plugin manifest mentions `workflows` and "agent team" features, which I did not read.
